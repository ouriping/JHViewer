1. 背景与目标

1.1 现状

仓库已有：

能力 位置 局限
单文件/目录导出 HTML SiteExportService / DirectorySiteExportService 一次性导出，无树形导航体验
本地静态站点托管 LocalWebHostService 只读静态文件，不能在线编辑
Markdown 编辑 MarkdownEditorControl 桌面端编辑，与 Wiki 站点未闭环

现有「发布中心」适合临时预览，不适合作为长期维护的帮助文档 Wiki。

1.2 产品目标

新建独立项目 MarkdownWiki，实现：

  1. 多 .md 文档 → 目录树：按文件夹层级自动生成导航树
  2. Web 方式访问 Wiki：浏览器打开即可阅读帮助文档
  3. 编辑与管理：新建 / 重命名 / 移动 / 删除文档与文件夹
  4. 保存即更新：编辑保存后 Wiki 页面立即可见（无需手动再导出）

1.3 非目标（首版不做）

  • 多用户账号体系与细粒度权限（可预留接口）
  • 公网部署、HTTPS 证书托管、CDN
  • 实时协同编辑（多人同时改同一文件）
  • 完整 Git 版本管理 UI（可后续接）

2. 用户故事

角色 故事 验收要点
读者 打开浏览器访问 Wiki，左侧树点选文档阅读 树结构与磁盘目录一致；Markdown 正确渲染
作者 在 Web 端编辑某篇 .md 并保存 刷新后内容已更新；磁盘文件已写入
管理员 新建文档/文件夹，调整树结构 树即时刷新；路径合法且无穿越
运维 指定文档根目录与端口后一键启动 本机可访问；可选局域网

3. 总体架构

3.1 推荐方案：ASP.NET Core 一体式 Wiki

┌─────────────────────────────────────────────────────────┐
│                    MarkdownWiki (Web)                    │
│  ┌─────────────┐  ┌──────────────┐  ┌─────────────────┐ │
│  │ 阅读页       │  │ 管理/编辑页   │  │ REST API        │ │
│  │ /wiki/{path}│  │ /edit/{path} │  │ /api/tree,docs  │ │
│  └──────┬──────┘  └──────┬───────┘  └────────┬────────┘ │
│         └────────────────┼───────────────────┘          │
│                          ▼                              │
│              ┌───────────────────────┐                  │
│              │   Wiki 领域服务层      │                  │
│              │ Tree / Doc / Watcher  │                  │
│              └───────────┬───────────┘                  │
│                          ▼                              │
│              ┌───────────────────────┐                  │
│              │  文档根目录 (磁盘)      │                  │
│              │  wiki-content/**/*.md │                  │
│              └───────────────────────┘                  │
└─────────────────────────────────────────────────────────┘

为什么选这个方案：

对比项 增强现有 WinForms 发布中心 新建 ASP.NET Core Wiki（推荐）
Web 阅读体验 弱（静态 HTML） 强（布局+树+搜索可扩展）
在线编辑 需另做 原生支持
保存即更新 需反复导出 直接读写源 .md
与现有代码关系 耦合主程序 独立项目，可复用 Markdig 渲染思路
部署 依赖桌面程序常开 可单独 dotnet run / 服务化

与现有项目关系：

  • 不替换 MarkdownContextViewer（继续做桌面编辑与 Explorer 预览）
  • 新增 MarkdownWiki 专注帮助文档站点
  • 可选后续：桌面「发布中心」增加「打开 MarkdownWiki」入口

3.2 数据模型（源文件即真相）

不以数据库存正文，以磁盘 .md 为唯一数据源：

wiki-content/                 # 可配置的文档根目录
├── _meta/
│   └── wiki.json             # 站点标题、首页、忽略规则等
├── index.md                  # 默认首页
├── getting-started/
│   ├── install.md
│   └── quick-start.md
└── guide/
    ├── overview.md
    └── faq.md

树节点规则：

  • 文件夹 → 树节点（可展开）
  • .md 文件 → 叶子文档节点
  • 忽略：_meta、. 开头、可配置扩展名黑名单
  • URL 路径 = 相对根目录的 POSIX 路径（如 /wiki/guide/faq）

4. 技术选型

层级 技术 说明

前端布局 服务端渲染 + 少量 JS 左侧树、右侧内容；编辑器用 textarea 或简易 CodeMirror

测试 xUnit（核心服务） 树构建、路径安全、CRUD

首版不引入：数据库、Identity、SignalR（后续热刷新可加）。

6. 核心模块设计

6.1 WikiTreeService

职责： 扫描文档根，构建内存树，支持缓存与失效。

public sealed class WikiNode
{
    public required string Name { get; init; }          // 显示名
    public required string RelativePath { get; init; }  // 相对根，POSIX
    public required WikiNodeKind Kind { get; init; }    // Folder | Document
    public List<WikiNode> Children { get; init; } = [];
}

public enum WikiNodeKind { Folder, Document }

接口草案：

  • WikiNode GetTree()
  • void Invalidate()
  • 排序：文件夹优先，再按名称（可配置）

6.2 WikiDocumentService

方法 行为
Get(relativePath) 读 .md 原文 + 元数据（标题取首个 # 或文件名）
Save(relativePath, content) 原子写（写临时文件再替换）
CreateDocument(parent, name) 新建空 .md
CreateFolder(parent, name) 新建目录
Rename(path, newName) 重命名
Move(from, toParent) 移动
Delete(path) 删除文件或空目录（目录非空需确认策略）

6.3 WikiPathGuard（关键关键）

  • 所有相对路径规范化后必须落在文档根内
  • 禁止 ..、绝对路径、盘符、空段
  • 仅允许 .md 作为文档扩展名（资源文件策略见阶段 3）
  • API 与页面共用同一守卫

6.4 WikiRenderService

  • 输入 Markdown 文本 → 输出 HTML 片段
  • 扩展：管道、表格、任务列表、自动链接（与桌面端对齐）
  • 相对图片链接：映射到文档相对路径下的静态文件服务（阶段 3）

6.5 WikiContentWatcher

  • 监听文档根 Created/Changed/Deleted/Renamed
  • 防抖后 Invalidate 树缓存
  • Web 端可通过「刷新树」或后续 SSE/SignalR 推送

7. Web 界面与 API

7.1 页面

路由 说明
/ 重定向到配置的首页文档（默认 index.md）
/wiki/{**path} 阅读：左树 + 右 HTML
/edit/{**path} 编辑：左树 + 右编辑器 + 保存/预览
/manage 管理：新建文档/文件夹、删除、重命名

布局草图：

+------------------+----------------------------------+
| 站点标题          |  [阅读] [编辑] [管理]  搜索(后期) |
+------------------+----------------------------------+
| 📁 getting-start |  # 标题                           |
|   └ install      |  正文 HTML...                     |
|   └ quick-start  |                                  |
| 📁 guide         |                                  |
|   └ overview ★   |                                  |
+------------------+----------------------------------+

7.2 API（供页面与后续桌面端调用）

方法 路径 说明
GET /api/tree 返回整棵树 JSON
GET /api/docs/{**path} 返回 Markdown 原文
PUT /api/docs/{**path} 保存正文
POST /api/docs 新建文档 { parent, name }
POST /api/folders 新建文件夹
PATCH /api/nodes 重命名/移动
DELETE /api/nodes/{**path} 删除

响应统一：{ ok, data?, error? }。

7.3 配置项（appsettings.json）

{
  "Wiki": {
    "ContentRoot": "../samples/wiki-content",
    "SiteTitle": "Jinghua 帮助文档",
    "HomeDocument": "index.md",
    "AllowLan": false,
    "Port": 5099,
    "EnableEdit": true
  }
}
  • AllowLan = false → 绑定 127.0.0.1
  • AllowLan = true → 绑定 0.0.0.0 并启动时警告
  • EnableEdit = false → 只读模式（只隐藏编辑入口 + API 拒绝写操作）

10. 安全要求

  1. 默认仅本机访问
  2. 所有文件操作经 WikiPathGuard
  3. 编辑功能可一键关闭（只读 Wiki）
  4. 删除操作二次确认（前端）+ 服务端校验
  5. 不对用户 Markdown 做任意服务端脚本执行；渲染侧注意 HTML 消毒策略（Markdig 默认转义 + 可选允许安全标签）

11. 风险与对策

风险 对策
大目录扫描慢 树缓存 + Watcher 增量失效；必要时懒加载子树
并发保存冲突 首版单写者；后期可用 ETag / 文件时间戳乐观锁
局域网误开放 UI/日志明确提示；默认 AllowLan=false
与桌面编辑器同时改同一文件 Watcher 刷新；编辑页打开时提示「外部已修改」（阶段 3）

1. 背景与目标

1.1 为什么需要 CHM

形态 优点 局限
MarkdownWiki（Web） 在线编辑、实时更新、易分享局域网 需服务常开；离线分发不便
静态 HTML 导出 简单 多文件目录，读者需自己点开
CHM（Compiled HTML Help） 单文件、Windows 原生目录树、全文搜索、离线分发 偏遗留格式；需编译器；跨平台弱

产品目标： 把文档根目录（多份 .md + 图片）一键打包为单个 .chm，方便随软件安装包分发或邮件传递。

1.2 用户故事

角色 故事 验收
文档管理员 在管理后台点「导出 CHM」 得到可双击打开的 .chm，目录树与 Wiki 一致
软件发布人员 构建流水线生成帮助包 命令行可导出；失败有明确日志
最终用户 打开 Help.chm 查文档 左侧 TOC、默认首页、图片正常、可搜索

1.3 非目标（首版）

  • 在 CHM 内在线编辑
  • 替代 MarkdownWiki Web 阅读站
  • 完整 PDF/ePub 多格式（可后期扩展）
  • 自研 CHM 二进制格式读写（优先调用成熟编译器）

2. CHM 标准结构（规范依据）

Microsoft HTML Help 1.x 工程通常包含：

chm-build/                     # 中间构建目录
├── html/                      # 由 .md 转换的 HTML（保留相对目录）
│   ├── index.htm
│   ├── getting-started/
│   │   └── install.htm
│   └── guide/
│       └── faq.htm
├── assets/…                   # 图片等（或跟在各页相对路径下）
├── Project.hhp                # 工程文件
├── TableOfContents.hhc        # 目录（Contents）
├── Index.hhk                  # 索引（可选，首版可自动生成标题词条）
└── Project.chm                # 编译产物

2.1 .hhp（工程）要点

[OPTIONS]
Compatibility=1.1 or later
Compiled file=Output.chm
Contents file=TableOfContents.hhc
Index file=Index.hhk
Default topic=html\index.htm
Title=Jinghua 帮助文档
Language=0x804 中文(中国)
Default Font=Microsoft YaHei,9,0
Full-text search=Yes
Binary TOC=Yes

[FILES]
html\index.htm
html\getting-started\install.htm
...

2.2 .hhc（目录树）

HTML 片段式 sitemap，节点对应文件夹 / 文档，与 Wiki 树同构：

<!DOCTYPE HTML PUBLIC "-//IETF//DTD HTML//EN">
<HTML><BODY>
<OBJECT type="text/site properties">
  <param name="FrameName" value="right">
</OBJECT>
<UL>
  <LI><OBJECT type="text/sitemap">
    <param name="Name" value="安装说明">
    <param name="Local" value="html\getting-started\install.htm">
  </OBJECT>
  ...
</UL>
</BODY></HTML>

2.3 编译器选型（推荐双后端）

编译器 来源 许可/获取 备注
hhc.exe（首选） Microsoft HTML Help Workshop 免费，遗留工具 Windows 经典方案；成功时常返回 exit code 1（历史 quirk，需按「文件是否生成」判定）
chmcmd（备选） Free Pascal / Lazarus 开源 可放 PATH；适合未装 Workshop 的环境

行业惯例（md2chm、Doxygen 等）：先生成 HTML + HHP/HHC，再调用外部编译器。不在 .NET 内手写 CHM 压缩包格式。

本项目推荐：
Markdown → HTML（自研/复用 Markdig）→ 生成 HHP/HHC/HHK → 调用 hhc.exe 或 chmcmd。

4. 关键设计细节

4.1 HTML 约束（CHM 兼容）

  1. 扩展名：优先 .htm（Workshop 传统习惯；.html 一般也可用，首版统一 .htm）。
  2. 字符集：<meta charset="utf-8"> + 可选 BOM；Title 用文档首个 # 标题。
  3. 链接改写：
    • xxx.md → xxx.htm
    • 图片 assets/a.png 保持相对路径并复制文件
  4. CSS：内联一份精简样式到每页或共享 css/chm.css 并列入 [FILES]。
  5. 避免：依赖现代 ES Module、外网 CDN、复杂 JS（CHM 内 IE 内核行为偏旧）。

4.4 编译器探测顺序

  1. ChmExportOptions.CompilerPath（显式配置）
  2. %ProgramFiles(x86)%\HTML Help Workshop\hhc.exe
  3. %ProgramFiles%\HTML Help Workshop\hhc.exe
  4. PATH 中的 hhc.exe / chmcmd.exe

4.5 成功判定（重要）

  • 不要仅用 hhc.exe 的 exit code（成功常为 1）。
  • 判定：目标 .chm 存在且长度 > 0，且（可选）修改时间在本次编译之后。

4.6 安全与分发提示

  • 从网络下载的 CHM，Windows 可能「锁定」导致空白页 → 文档中说明「属性 → 解除锁定」。

多格式预览与引擎切换 — 开发需求

版本：v0.1
日期：2026-09-30
状态：方案已选定，分阶段实现
关联：docs/预览窗格.md、MarkdownPreview.Handler、MarkdownEditorControl

1. 背景与目标

1.1 现状

能力 现状
资源管理器预览窗格 仅 .md；引擎由 %LocalAppData%\MarkdownContextViewer\preview-engine.txt 决定，窗格内无法切换
主程序编辑预览 WebBrowser / WinFormsMarkdownView；引擎切换在主菜单「查看」
JSON / XML 不支持

1.2 目标

  1. 预览窗格内可切换 Web / WinForms，并标明性能差异。
  2. 主程序与预览窗格共用同一引擎设置，切换即时生效。
  3. 规划扩展到 JSON、XML 等文本类型；选定架构后分阶段落地。

1.3 非目标（首版）

  • 完整插件市场 / 热插拔第三方 DLL（可留扩展点）
  • PDF、图片、Office 等非纯文本预览
  • 替换现有 SharpShell COM 宿主

2. 引擎对比（给用户的标注依据）

维度 Web（WebView2 / WebBrowser） WinForms（RichTextBox）
启动速度 较慢（需初始化浏览器内核） 更快 ★推荐轻量场景
大文件滚动 一般依赖 DOM 更轻、更稳 ★
Markdown 还原度 高（HTML/CSS/表格/代码块）★ 低（标题/粗体/列表近似）
JSON / XML 可用 HTML 着色，开销更大 树控 + 文本，更合适 ★
依赖 WebView2 Runtime（Handler） 无额外运行时
内存 偏高 更低 ★

产品文案建议（写在按钮/Tooltip）：

  • Web（还原度高） — 适合看 Markdown 排版效果
  • WinForms（更快更省） — 适合大文件、快速浏览、JSON/XML

默认引擎：仍建议 Web（保证 Markdown 观感）；用户可切到 WinForms 追求性能。

3. 多格式方案对比：插件 vs 进程内界面

3.1 方案 A：独立插件（MEF / 动态加载 DLL）

MarkdownPreview.Handler (宿主)
  └─ Plugins/
       ├─ MdPreview.dll
       ├─ JsonPreview.dll
       └─ XmlPreview.dll
优点 缺点
扩展解耦，第三方可贡献 COM 预览宿主进程隔离下加载复杂
按需部署 版本/依赖冲突；调试成本高
首版仅 3 种格式，投入产出比低

3.2 方案 B：原项目内增加界面 + 按扩展切换 UserControl（推荐）

PreviewHostControl（工具栏 + 引擎切换 + 内容区）
  └─ 按扩展名选择 IDocumentPreviewProvider
       ├─ MarkdownPreviewProvider → WebView / WinFormsMarkdownView
       ├─ JsonPreviewProvider     → TreeView + 文本（或 Web 着色）
       └─ XmlPreviewProvider      → TreeView + 文本
优点 缺点
与现有 Handler / 主程序一致，易维护 格式变多后程序集体积增大
一套 COM 注册可挂多个扩展名 不如插件「可单独卸载」
设计器可直接改各格式控件
后期仍可抽出接口做成插件

3.3 结论（选定）

采用方案 B：进程内 Provider + 宿主切换视图。

理由：

  1. 预览窗格跑在 prevhost.exe，插件加载/卸载不稳定，与 SharpShell 冲突风险高。
  2. JSON/XML 与 Markdown 同属「文本结构化预览」，放同一解决方案最自然。
  3. 先定义 IDocumentPreviewProvider，将来若要插件，只需再做一个 PluginPreviewLoader，不必推翻宿主。

不做首版插件系统；保留接口作为扩展点。

Markdown 导出与网站访问功能设计说明

网站访问功能设计说明.md

Markdown 导出与网站访问功能设计说明

1. 目标

在现有 WinForms Markdown 编辑器基础上，新增两类能力：

  1. 一键导出到程序运行目录并以网站方式访问
  2. 指定一个文档目录，按文件夹结构提供网站访问

并确保：

  • 本地可用、操作简单
  • 不影响现有编辑流程
  • 后续可扩展为局域网访问

2. 推荐实现方案（最佳实践）

推荐采用 双模式 + 本地轻量 HTTP 服务：

模式 A：一键导出当前文档（或全部已打开文档）

  • 将 .md 转换为 .html
  • 输出到程序目录下：./site-output/
  • 自动生成 index.html
  • 启动本地站点：http://127.0.0.1:5088

模式 B：开放指定文档目录为网站

  • 用户选择一个目录（例如 D:\docs）
  • 程序扫描目录树中的 .md
  • 动态生成导航树页面
  • 通过本地地址访问和浏览

推荐默认只绑定 127.0.0.1，更安全；需要时再开放到 0.0.0.0（局域网可访问）。

3. 为什么这是“最好”的方案

  1. 易用：对用户是“一个按钮”就能发布并浏览。
  2. 风险低：默认仅本机访问，不暴露公网。
  3. 兼容现有结构：只增加服务类，不破坏现有编辑控件。
  4. 可扩展：后续可加搜索、目录索引、主题、权限控制。

4. 代码结构建议

新增服务类：

  • SiteExportService.cs

    • 输入：Markdown 文本或文件路径
    • 输出：site-output 目录下的 HTML 文件
    • 职责：
      • .md -> .html
      • 复制静态资源（CSS/JS）
      • 生成 index.html 导航页

  • LocalWebHostService.cs

    • 职责：启动/停止本地 HTTP 服务
    • 推荐：HttpListener 或第三方轻量库（如 EmbedIO）
    • 提供：
      • Start(rootPath, port, host)
      • Stop()

  • SiteIndexBuilder.cs（可选）

    • 职责：根据目录树生成导航 HTML（树状列表）

5. UI 改造建议

在主界面顶部新增分组（“发布”）：

  1. 导出当前为网站 按钮
  2. 导出全部打开文档 按钮
  3. 选择目录并启动网站 按钮
  4. 停止网站 按钮
  5. 端口输入框（默认 5088）
  6. “打开浏览器”按钮

提示信息建议：

  • 导出成功路径
  • 当前访问 URL
  • 端口占用时的错误提示

6. 访问路径设计

建议统一规则：

  • 首页：/ -> index.html
  • 文档页：/docs/xxx.html
  • 静态资源：/assets/...

如果是目录模式：

  • 保留目录结构映射，比如：
    • D:\docs\A\B\readme.md
    • 网站路径：/docs/A/B/readme.html

7. 实施步骤（落地顺序）

第一步（最小可用）

  • 做“导出当前文档到运行目录”
  • 自动打开默认浏览器访问 index.html

  • 加本地 HTTP 服务

  • 主题切换（可选）

  1. Markdown 渲染：沿用现有 Markdig。
  2. HTML 模板：抽成统一模板（头部样式 + 内容容器）。

预览窗格

预览窗格.md

在Windows 11的文件资源管理器中，为.md文件实现Markdown格式的预览窗格，其核心是开发一个预览处理程序（Preview Handler）。这是一个基于COM的Shell扩展，当用户在资源管理器中选中文件时，它会被调用，并在预览窗格中渲染文件内容，而无需启动完整的编辑器应用。

下面我将从实现原理、技术选型和开发流程几个方面为你详细拆解。

🔧 实现原理与架构

预览处理程序的工作机制如下：

  1. COM接口实现：你的C#程序需要实现IPreviewHandler等COM接口，这是与Windows Shell通信的契约。
  2. 进程隔离：出于安全考虑，预览处理程序通常在进程外运行。Windows会通过一个名为Prevhost.exe的代理进程来托管你的处理程序，这能有效防止因预览器崩溃而影响资源管理器本身。
  3. 文件关联：你需要在Windows注册表中，将.md文件扩展名与你的预览处理程序（通过其CLSID）进行关联。这样，当用户选中一个.md文件时，资源管理器就知道该调用哪个处理程序来生成预览。
  4. 渲染流程：处理程序被激活后，会接收到一个窗口句柄（Handle），你的代码需要在这个窗口区域内，将Markdown文本渲染成可视化的HTML内容。

🛠️ C#开发技术选型

使用C#开发，主要有以下两种成熟的技术路径：

方案 核心思路 优点 缺点
方案一：SharpShell框架 使用SharpShell这个.NET库来简化COM接口的封装和注册。你只需继承SharpPreviewHandler类，并重写DoPreview方法即可。 开发效率高，SharpShell处理了复杂的COM互操作和注册表操作，让开发者能专注于预览内容的渲染逻辑。 需要引入额外的第三方依赖。
方案二：原生COM互操作 直接在C#中手动定义并实现IPreviewHandler等所有必需的COM接口。 完全可控，不依赖第三方库，能更深入地理解底层机制。 开发难度大，需要处理大量的COM互操作细节，代码量大且容易出错。

对于快速开发，强烈推荐方案一。接下来我们将以SharpShell为例。

📝 开发与部署流程（基于SharpShell）

第1步：创建项目并引入依赖

  1. 在Visual Studio中创建一个类库（.NET Framework） 项目。注意，SharpShell目前主要针对.NET Framework。
  2. 通过NuGet安装必要的包：
    • SharpShell：核心框架。
    • Markdig：高性能的Markdown解析库，用于将.md文本转换为HTML。
    • Microsoft.Web.WebView2：用于在预览窗格中显示渲染后的HTML内容。

第2步：实现预览处理程序类

创建一个类，继承自SharpPreviewHandler，并实现核心的DoPreview方法。以下是一个简化的代码示例：

using SharpShell.Attributes;
using SharpShell.SharpPreviewHandler;
using Markdig;
using Microsoft.Web.WebView2.WinForms;
using System.IO;
using System.Runtime.InteropServices;
using System.Windows.Forms;

// 1. 将此类的COM可见性设为true
[ComVisible(true)]
// 2. 将处理程序与.md扩展名关联
[COMServerAssociation(AssociationType.ClassOfExtension, ".md")]
public class MarkdownPreviewHandler : SharpPreviewHandler
{
    // 3. 在此方法中实现渲染逻辑
    protected override PreviewHandlerControl DoPreview()
    {
        // 创建承载WebView2的自定义控件
        var control = new MarkdownPreviewControl();
        // 读取Markdown文件内容
        var filePath = SelectedItemPath;
        if (File.Exists(filePath))
        {
            var markdownText = File.ReadAllText(filePath);
            // 使用Markdig将Markdown转换为HTML
            var html = Markdown.ToHtml(markdownText);
            // 将HTML传递给控件进行显示
            control.SetHtmlContent(html);
        }
        return control;
    }
}

第3步：创建承载WebView2的自定义控件

SharpPreviewHandler需要一个PreviewHandlerControl来显示内容。由于我们要显示HTML，最好使用WebView2。

using Microsoft.Web.WebView2.WinForms;
using SharpShell.SharpPreviewHandler;
using System.Windows.Forms;

public class MarkdownPreviewControl : PreviewHandlerControl
{
    private WebView2 _webView;

    public MarkdownPreviewControl()
    {
        _webView = new WebView2();
        _webView.Dock = DockStyle.Fill;
        this.Controls.Add(_webView);
        // 异步初始化WebView2环境
        InitializeWebView();
    }

    private async void InitializeWebView()
    {
        await _webView.EnsureCoreWebView2Async(null);
    }

    public void SetHtmlContent(string html)
    {
        if (_webView.CoreWebView2 != null)
        {
            // 加载HTML字符串
            _webView.CoreWebView2.NavigateToString(html);
        }
        else
        {
            // 如果环境尚未准备好，可以稍后重试或使用事件处理
            _webView.CoreWebView2InitializationCompleted += (sender, args) =>
            {
                if (args.IsSuccess)
                {
                    _webView.CoreWebView2.NavigateToString(html);
                }
            };
        }
    }
}

第4步：注册COM组件

开发完成后，需要将DLL注册到系统中。使用SharpShell，你可以通过其提供的ServerRegistrationManager工具或编写简单的安装程序来执行注册。注册过程会创建必要的注册表项，将.md文件与你的处理程序关联起来。

注册的核心注册表路径示例如下：

  • HKEY_CLASSES_ROOT\.md -> 指向一个ProgID（例如 MarkdownFile）
  • HKEY_CLASSES_ROOT\MarkdownFile\shellex\{8895b1c6-b41f-4c1c-a562-0d564250836f} -> 指向你的处理程序的CLSID
  • HKEY_CLASSES_ROOT\CLSID\{你的处理程序CLSID} -> 包含InprocServer32等键，指向你的DLL路径。

第5步：在Windows 11中验证

完成注册后，在Windows 11文件资源管理器中，点击“查看” -> “显示” -> “预览窗格”。选中一个.md文件，你应该就能在右侧看到渲染后的Markdown预览了。

⚠️ 注意事项与优化建议

  • 安全性：从文件读取内容并在WebView2中渲染HTML时，务必对HTML进行 sanitize（净化），移除潜在的恶意脚本（如<script>标签），防止XSS攻击。Markdig等库可能提供净化选项，或者你可以使用专门的HTML净化库。
  • 性能：对于非常大的Markdown文件，渲染可能会变慢。可以考虑设置一个文件大小上限，或进行异步渲染。
  • Windows 11兼容性：Windows 11在64位句柄处理上与旧版系统有差异，可能导致预览处理程序崩溃。开发时需确保正确处理IntPtr类型，避免将其错误地解析为32位整数。
  • 调试：调试预览处理程序比较特殊，因为它在Prevhost.exe进程中运行。你可以通过Visual Studio的“附加到进程”功能，附加到prevhost.exe进程进行调试。
